# 项目瘦身

在用户需要保留的功能、历史资产可恢复性和恢复成本之间，推荐切实可行的空间方案。先调查，再判断；不要预设某类文件一定可删，也不要因为是历史文件就一律保留。

## 范围与权限

- 默认只读分析并在对话中报告。不自动打包、移动、删除、安装依赖或运行会产生文件的构建、测试；用户要求保存报告时才写入指定位置。
- 读取目标项目适用的 AGENTS.md 和已有归档说明。以用户选定的项目为边界，不扩展到整块磁盘；不跟随符号链接、目录连接扫描外部目录，不读取无关凭据内容。
- 用户已批准具体执行清单时，直接执行覆盖的批次，无需逐文件再次询问。新目标、额外删除范围或恢复条件发生实质变化时，先说明并获得批准。
- 本技能的安装不代表对任意项目的整理授权。只在用户主动调用时使用。

## 先形成证据

1. 确认项目当前用途、应保留的功能与用户目标。可以从项目文档和代码推断时先调查；只有影响推荐的关键信息缺失才提问。
2. 统计总量、文件数、主要目录、占用最大的文件组及小文件分布。先看高收益位置，避免为了报告做无关的全量内容审计。
3. 检查入口、构建配置、依赖引用、现有忽略规则、历史说明和生成方式。文件名、修改时间或没有搜到引用，单独都不能证明可删。
4. 将候选项分成：当前必需、可重新生成、暂时不用但有保留价值、用途待确认。说明恢复是否依赖网络、授权、旧版本工具或不再可用的输入。
5. 区分已经验证、静态证据支持、尚未验证。分析阶段不为了声称“稳定”擅自运行构建或测试；执行授权包含验证时，采用能覆盖实际影响的最小检查。

明确统计口径：逻辑大小和磁盘实际占用可能不同。硬链接、稀疏文件、压缩、重复统计及回收站都会影响实际收益；无法获得实际占用时标注估算，不声称精确释放量。缓存可再生，也可能很快重新占满。

## 给出可比较的方案

默认提供“低影响、推荐、激进”三档；只有确实存在有意义的差异才拆档。用户指定比例或容量时据此评估，不强凑 50%–90% 等目标。达不到时说明限制。

每档回答：

- 当前大小、预计释放量和剩余量；删除、归档、保留清单以相对路径或明确文件组列出，附大小、数量和依据。
- 哪些功能仍能使用，哪些需要重建或恢复，已经验证什么，还有哪些不确定性。
- 归档后的恢复步骤、最小下载/解压范围和主要成本；可删除项的重建条件。
- 相对上一档增加的空间收益与代价，并推荐一档及理由。

各动作集合互斥，不把父目录和子项、原件与其压缩副本重复计入释放量。归档只有在本地副本实际释放后才计入收益；保留的压缩包、临时文件和元数据仍占空间。移到同一磁盘其他目录或回收站不算该磁盘已经腾出空间。

## 打包建议必须随归档方案给出

Agent 应根据当前项目决定是否打包、如何分组和多大一包，不要求用户先选择技术参数，也不把固定 MB 数当作所有项目的标准。

### 分组和颗粒度

- 优先按“一起恢复、一起使用”的目录、任务、版本或资产组划分，包内保留相对路径；每包建议能独立解压。
- 大文件、已压缩格式或经常单独恢复的文件，可以直接归档；数量多且共同恢复的小文件更适合合包。说明打包是否主要减少文件数、改善组织，还是确有压缩收益。
- 根据文件大小分布、恢复频率、已知传输速度、失败重传成本、服务已知限制和本地临时空间，给出每组建议包大小范围、预计包数及理由。不知道速度或压缩率时写明假设并给范围，不编造实测或 API 限制。
- 不因某个大文件超过建议范围而强行拆分所有包。需要跨卷分卷时明确说明：这些卷通常相互依赖，缺一卷可能影响整个归档的恢复；不要把分卷冒充独立包。
- 压缩格式优先使用现有工具和容易恢复的格式。已压缩数据可采用仅存储模式，避免无收益的高强度压缩。没有实际需要不添加依赖。

建议用一张表：候选路径、原始大小/文件数、直接归档或打包、分组依据、建议单包范围、预计包数、恢复单位、理由。没有必要打包时也应明确写出判断。

### 体积与临时空间

- 包数根据实际分组和预计压缩后体积估算；分组完整性优先于机械凑满。压缩比未知时，不把乐观压缩率当作保证。
- 同一磁盘保留原件并生成压缩包时，峰值占用包含原件、输出包、工具临时文件及仍保留的其他副本；分别报告“额外可用空间需求”和“最终释放量”。恢复时也要考虑下载包与解压结果同时存在。
- 空间不足时，优先缩小独立批次或利用用户允许的其他存储位置。每批打包、验证、归档及原件释放必须满足授权和完整性条件，不能为腾空间提前删原件。

### 执行与校验

以下仅在执行授权覆盖时实施：

1. 在监听目录外生成包，完成并关闭文件后再交给归档程序，避免半成品被上传。
2. 保存每包成员清单、原始相对路径、大小和内容哈希，以及必要的恢复说明。清单随归档保存，不仅存在本机；覆盖重建目录所需的映射。不要把凭据或无关私密信息写进清单。
3. 验证包可读取、成员清单完整且路径无冲突；在释放原件之前，解压或流式读取包内内容并核对成员大小和哈希，确认原件未在打包期间变化。仅“压缩命令成功”不能证明可恢复。
4. 云端对压缩包的 SHA-256 校验只证明包本身传输一致，不能代替包内原始文件覆盖完整性的校验。失败或结果不明时保留原件并报告。

## 可选对接项目云空间

- 项目已有“云空间”时，先读其中的 AGENTS.md，按照它提供的程序位置与 Agent 接口操作，不假设安装在固定盘符。分析阶段只读取本地状态，不擅自启动上传或调用云端恢复。
- 执行归档前确认主程序运行且接收归档，核对暂停、冷却、失败状态。按批准的目录映射交付文件；不要随意扁平化路径。
- 保留云空间自带的说明、快捷方式、配置和 .云端记录。不要将这些文件打包或作为瘦身对象。
- 归档完成以程序协议为准：完整回读的大小和 SHA-256 校验、云端索引备份及核对、本地记录持久化成功之后，才由程序释放其管理的源文件。上传进度 100%、窗口心跳或文件暂时不见都不能单独证明完成。
- 上传压缩包只会由程序释放被归档的压缩包，包外的原始文件不会因此自动释放。只有原件清理也在批准范围内、包内完整性已验证、归档完成可确认且原件未变化，才可按清单清理包外原件。
- 恢复压缩包后仍需解压并按清单还原。不要声称云空间的整项目恢复会自动恢复包内文件。

## 交付

分析结束时给出推荐方案、具体候选清单、打包建议、净收益和未验证项，使用户能直接批准一个明确批次。用户只要分析时，不继续执行。

已获执行授权时，按批次处理并验证；报告实际完成、失败、保留内容、实际空间变化与恢复入口。估算值与实测值分开，不把进入队列当作归档成功。
